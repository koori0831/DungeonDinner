# 재료 획득 시스템 구현 명세서 인덱스

## 1. 목적

이 문서 묶음은 `파견`과 `모험`을 처음부터 끝까지 구현하기 위한 실행용 명세서다.

기존 문서 역할:

- `Material_Acquisition_Dispatch_Adventure_Planning.md`: 게임 디자인 방향
- `Material_Acquisition_Dispatch_Adventure_Implementation_Rules.md`: 구현 규칙과 코딩 원칙
- `Material_Acquisition_Dispatch_Adventure_Implementation_Spec.md`: 1차 로드맵 요약

이 폴더의 문서 역할:

- 실제 구현 순서
- 클래스와 데이터 구조
- UI 흐름
- 저장과 테스트
- 사용자 결정 필요 지점
- 단계별 완료 조건

## 3. 구현 의존성

```text
영업 종료/준비 단계
  -> 공통 보상/랜덤/인벤토리
    -> 파견
    -> 모험
      -> 데이터/밸런스
        -> UI/저장/테스트 마감
```

파견과 모험은 서로 독립 콘텐츠지만, 아래 기반은 반드시 공유한다.

- 현재 영업일 조회
- 준비 단계 진입 가능 여부
- 보상 테이블
- 시드 기반 랜덤
- 인벤토리 지급 결과
- 새 재료 발견 결과
- 저장 ID 규칙

## 4. 권장 작업 순서

### Step 1. 준비 단계와 날짜 루프

목표:

- 손님 응대가 끝났을 때 준비 단계로 진입한다.
- 준비 단계에서 파견, 모험, 다음날 시작을 선택한다.
- 다음날 시작 시 영업일이 증가한다.

주요 산출물:

- `PreparationPhaseController`
- `PreparationPhaseState`
- `PreparationPhaseView`
- `IAcquisitionDayProvider`
- `NpcEncounterDayProvider`

사용자 결정 필요:

- 하루에 파견과 모험을 모두 할 수 있는지
- 준비 단계에서 다음날 시작 전에 결과 수령을 강제할지
- 준비 단계 화면의 기본 UI 방향

### Step 2. 공통 보상 기반

목표:

- 파견과 모험이 같은 보상 결과 모델을 사용한다.
- 보상 계산은 UI와 분리한다.
- 인벤토리 부족 결과가 사라지지 않는다.

주요 산출물:

- `AcquisitionRewardTableSO`
- `AcquisitionRewardEntry`
- `AcquisitionRewardResolver`
- `SeededAcquisitionRandom`
- `AcquisitionInventoryGateway`
- `AcquisitionRewardResult`

사용자 결정 필요:

- 희귀도 명칭
- 희귀 확률 공개 방식
- 새 재료 발견 표시 방식

### Step 3. 파견 MVP

목표:

- 지역과 NPC를 선택해 영업일 단위 파견을 시작한다.
- N일 뒤 복귀 결과를 수령한다.
- 결과 수령 시 인벤토리에 재료를 지급한다.

주요 산출물:

- `DispatchRegionSO`
- `DispatchAgentSO`
- `DispatchTask`
- `DispatchService`
- `DispatchResultResolver`
- `DispatchScreen`

사용자 결정 필요:

- 1차 파견 지역 3개
- 1차 파견 NPC 2명
- 파견 중 NPC가 손님으로 등장 가능한지
- 지역별 보상과 위험도

### Step 4. 모험 MVP

목표:

- 지역을 선택해 모험 세션을 시작한다.
- 이벤트와 선택지를 통해 위험도와 임시 보상을 변경한다.
- 귀환 또는 종료 시 정산한다.

주요 산출물:

- `AdventureRegionSO`
- `AdventureEventSO`
- `AdventureChoice`
- `AdventureSession`
- `AdventureService`
- `AdventureSettlementService`
- `AdventureScreen`

사용자 결정 필요:

- 1차 모험 지역 1개
- 이벤트 6개와 선택지 문구
- 위험도 최대치와 실패 조건
- 실패 시 보상 손실 정책

### Step 5. 데이터, UI, 저장, 테스트 마감

목표:

- 데이터가 에디터에서 검증된다.
- UI 프리팹으로 최종 화면을 구성한다.
- 저장과 로드가 가능하다.
- 도메인 테스트로 회귀를 막는다.

주요 산출물:

- `AcquisitionDataValidator`
- `AcquisitionSaveData`
- `DispatchSaveData`
- `AdventureSaveData`
- UI 프리팹 세트
- 도메인 테스트

사용자 결정 필요:

- 저장 타이밍
- 모험 중 게임 종료 후 재개 정책
- 최종 UI 레이아웃과 연출 우선순위

## 5. 구현 범위 구분

### 5.1 1차 필수

- 영업 종료 후 준비 단계
- 다음날 진행
- 공통 보상 테이블
- 인벤토리 지급 결과
- 파견 지역 3개
- 파견 NPC 2명
- 영업일 단위 파견
- 파견 복귀 결과 수령
- 모험 지역 1개
- 이벤트 6개
- 선택지 기반 모험 진행
- 위험도
- 귀환 정산
- 기본 저장 또는 메모리 저장소
- 최소 테스트

### 5.2 1차 선택

- 도감 갱신 UI
- 파견 실패/부분 성공 상세 연출
- 모험 피로도
- 도구 조건
- 지역 해금
- 레시피 힌트
- NPC 특성별 고급 보너스

### 5.3 2차 이후

- 여러 모험 지역
- 이벤트 체인
- 숨겨진 결과
- 파견 숙련도
- 지역별 소문/정보 시스템
- 고급 도감 연동
- 사운드/애니메이션 연출
- 세이브 마이그레이션

## 6. 사용자 개입 총정리

아래 항목은 구현 중 사용자에게 반드시 확인해야 한다.

| 시점 | 질문 | 기본 제안 |
| --- | --- | --- |
| 개발 시작 전 | 하루에 파견과 모험을 둘 다 가능한가 | 가능 |
| 개발 시작 전 | 하루 파견 가능 NPC 수 | 1명 |
| 개발 시작 전 | 파견 중 NPC가 손님으로 등장 가능한가 | 등장 불가 |
| 파견 데이터 작성 전 | 1차 파견 지역 3개는 무엇인가 | 근처 숲, 축축한 동굴, 소금 동굴 |
| 파견 데이터 작성 전 | 1차 파견 NPC 2명은 누구인가 | 기존 NPC 중 2명 선택 필요 |
| 모험 데이터 작성 전 | 1차 모험 지역은 무엇인가 | 축축한 동굴 |
| 모험 데이터 작성 전 | 실패 시 보상을 잃는가 | 일부 손실 |
| UI 작업 전 | 파견 화면은 지도형인가 목록형인가 | 1차는 목록형 |
| UI 작업 전 | 모험 화면은 텍스트 로그형인가 장면 연출형인가 | 1차는 텍스트 로그형 |
| 저장 작업 전 | 모험 중 종료 시 재개 가능한가 | 1차는 같은 이벤트에서 재개 |

## 7. 최종 완료 정의

아래가 모두 충족되면 1차 구현 완료로 본다.

- 손님 응대 중에는 파견과 모험을 열 수 없다.
- 영업 종료 후 준비 단계에서만 파견과 모험에 진입한다.
- 다음날 시작이 날짜 시스템과 연결된다.
- 파견은 시작 즉시 보상을 지급하지 않는다.
- 파견은 지정 영업일 뒤 복귀 가능 상태가 된다.
- 파견 결과 수령 시 인벤토리에 재료가 지급된다.
- 모험은 이벤트와 선택지 기반으로 진행된다.
- 모험 중 보상은 임시 보상으로 쌓인다.
- 귀환 또는 종료 정산 시 인벤토리에 재료가 지급된다.
- 파견과 모험은 공통 보상 결과 모델을 사용한다.
- 인벤토리 부족으로 미지급된 수량이 결과에 남는다.
- 새 재료 발견 여부를 결과에 담을 수 있다.
- 데이터 ID와 참조 오류를 검증할 수 있다.
- 핵심 도메인 로직은 UI 없이 테스트 가능하다.
