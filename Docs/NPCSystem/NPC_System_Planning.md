# NPC 시스템 기획 문서 1차본

## 1. 목적

`던전 한 끼`의 NPC는 단순히 랜덤 대사를 말하는 손님이 아니라, 플레이어가 요리를 추론하도록 돕는 핵심 장치다.

NPC 방문은 다음 경험을 만들어야 한다.

- 손님이 메뉴명을 직접 말하지 않는다.
- 플레이어는 대화, 추가 질문, 백과사전, 재료 지식을 조합해 원하는 음식을 추론한다.
- 요리 결과는 `정답 / 유사 정답 / 비정답 / 괴식`으로 판정된다.
- 좋은 응대는 호감도와 기억으로 남고, 재방문 이벤트로 이어진다.

현재 문서는 프로토타입에서 바로 만들 수 있는 범위를 기준으로 작성하되, 정식 버전에서 재방문, 호감도 이벤트, 연속 이벤트, 의뢰로 확장할 수 있게 구조를 열어둔다.

## 2. 핵심 구조

NPC 시스템의 중심 단위는 `NPC`가 아니라 `Visit Event`다.

```text
Visit Event = 대화 장면 + 자연스럽게 드러나는 주문 의도 + 질문 대화 + 정답 판정 + 결과 반응 + 완료 후 변화
```

예를 들어 `지친 초보 모험가`라는 NPC가 있다면, 실제 플레이에서 중요한 것은 이 NPC의 특정 방문 상황이다.

```text
지친 초보 모험가_첫방문_달콤한음료
지친 초보 모험가_호감도1_인사
지친 초보 모험가_재방문_스무디기억
```

NPC는 고정 정보와 기억을 가진다.

```text
NPC
- 이름
- 종족/직업
- 말투
- 선호/비선호 태그
- 기본 쿨다운
- 호감도
- 방문 기록
- 관련 Visit Event 목록
```

Visit Event는 한 번의 손님 응대를 구성한다.

```text
Visit Event
- 기본 대화 시퀀스
- 대화 속에서 드러나는 주문 의도
- 질문 카테고리별 짧은 질문 대화
- 정답 레시피
- 유사 정답 조건
- 결과별 반응
- 완료 후 호감도/기억/해금 변화
```

중요한 수정 방향:

```text
기존 느낌:
손님이 주문 단서를 말함
→ 플레이어가 질문함
→ 요리함

목표 느낌:
NPC와 플레이어가 서로 인사하고 반응함
→ 이전 기억이나 현재 상황을 대화함
→ 그 흐름 속에서 주문 의도가 자연스럽게 드러남
→ 필요하면 질문도 짧은 대화로 이어짐
→ 요리함
```

즉, NPC 방문은 `주문 접수`가 아니라 `대화 장면`이어야 한다.

예시:

```text
요른: 안녕하신가, 주인장!
플레이어: 어? 요른 씨, 또 오셨네요.
요른: 저번에 먹었던 마그마 큐브 음식을 잊지 못하겠어서, 주변에 수소문해 다시 찾아왔다네.
플레이어: 그렇게 말해주시니 너무 기쁘네요. 이번에는 어떤 요리를 해드릴까요?
요른: 이번에도 저번처럼 매콤하고 뜨거운 음식이 당기는군.
```

이 구조에서는 마지막 대사만 주문 단서가 아니다. 인사, 기억, 반응 전체가 NPC의 관계와 취향을 보여주는 단서가 된다.

## 3. 지역 NPC Pool

지역마다 NPC Pool이 존재한다.

```text
이끼 동굴 NPC Pool
- 지친 초보 모험가
- 광산길 정찰병
- 겁 많은 마법 견습생
```

일반 상황에서는 지역 Pool에서 NPC를 먼저 뽑고, 그 NPC의 가능한 Visit Event를 선택한다.

```text
지역 NPC Pool
→ NPC 선택
→ NPC 상태/기억 확인
→ 가능한 Visit Event 선택
→ 응대 진행
```

단, 중요한 이벤트는 Pool 추첨보다 우선할 수 있다.

```text
중요 이벤트 존재
→ 해당 Visit Event 우선 등장
→ 연결된 NPC가 등장
```

## 4. 하루 장사 흐름

하루 손님 수는 고정한다. 프로토타입 기준은 하루 3명이다.

손님은 장사 시작 시 미리 전부 뽑지 않고, 손님이 올 때마다 현재 상태를 기준으로 한 명씩 결정한다.

```text
장사 시작
→ 손님 슬롯 1 결정
→ 대화/질문/요리/반응
→ 호감도/기억/해금 갱신
→ 손님 슬롯 2 결정
→ 대화/질문/요리/반응
→ 손님 슬롯 3 결정
→ 장사 종료
```

기본 규칙:

- 같은 NPC는 같은 영업일에 기본적으로 한 번만 등장한다.
- 스토리상 필요한 경우만 예외를 둔다.
- 응대 결과는 즉시 반영되어 다음 손님 선정에 영향을 줄 수 있다.

## 5. Visit Event 우선순위

강제/우선 이벤트가 여러 개 있을 수 있으므로 우선순위를 둔다.

```text
1. 튜토리얼 / 메인 스토리 필수 이벤트
2. 지역 해금 / 진행 필수 이벤트
3. 호감도 단계 상승 이벤트
4. 강한 기억 / 재방문 이벤트
5. 진행 중인 연속 이벤트
6. 약한 기억 / 단골 이벤트
7. 일반 주문 이벤트
```

이 우선순위는 플레이어가 중요한 진행과 관계 보상을 놓치지 않도록 하기 위한 것이다.

## 6. 반복 정책

Visit Event는 반복 정책을 가진다.

| 반복 정책 | 용도 | 규칙 |
| --- | --- | --- |
| `NeverRepeat` | 첫 방문, 스토리, 강한 기억, 호감도 해금 | 한 번 발생하면 다시 후보에 들어가지 않는다. |
| `CycleRepeat` | 일반 주문, 일상 대화 | 반복 가능한 이벤트를 모두 본 뒤 다시 순환한다. |
| `CooldownRepeat` | 약한 기억, 단골 멘트 | 반복 가능하지만 최근 N회 방문 또는 N영업일 동안 제외한다. |

중요한 규칙:

- 첫 방문 이벤트는 모든 대화를 소진해도 다시 나오지 않는다.
- 강한 기억 이벤트도 대부분 1회성으로 둔다.
- 약한 기억 이벤트는 반복 가능하지만 너무 자주 나오지 않게 쿨다운을 둔다.
- 일반 주문은 순환 반복 가능하다.

## 7. 추가 질문 시스템

추가 질문은 카테고리형이다.

플레이어는 UI에서 카테고리를 고르고, 채팅창에는 짧은 질문 대화가 출력된다.

질문은 단순히 `플레이어 질문 1줄 → NPC 답변 1줄`로 끝나지 않아도 된다. 자연스럽게 느껴지는 경우에는 다음처럼 3~4줄의 짧은 대화로 구성한다.

```text
플레이어 질문
→ NPC가 생각하거나 반응함
→ NPC가 실제 단서를 말함
→ 플레이어가 단서를 확인하고 대화를 닫음
```

프로토타입 질문 카테고리:

```text
맛
온도/식감
몸 상태
피하고 싶은 것
```

질문 톤 원칙:

- 짧다.
- 일상적이다.
- 한 번에 하나만 묻되, 답변은 자연스러운 대화처럼 2줄까지 이어질 수 있다.
- 정답을 직접 말하게 하지 않는다.
- NPC 답변이 후보를 좁히는 단서가 된다.
- 마지막에 플레이어가 단서를 되짚거나 확인하면 대화가 더 살아난다.

예시:

```text
[맛]
플레이어: "최근에 좋아하시는 맛이 있으신가요?"
요른: "흠... 난 원체 웬만한 음식은 다 잘 먹어서."
요른: "아! 그래, 저번에 먹었던 마그마 큐브 음식의 단짠단짠이 예술이었는데 그런 음식이면 좋겠군."
플레이어: "단짠단짠... 넵, 알겠습니다. 조금만 기다려주세요!"

[온도/식감]
플레이어: "시원한 게 좋아요?"
NPC: "응. 목이 좀 말라."

[몸 상태]
플레이어: "많이 지치셨어요?"
NPC: "완전 녹초야. 씹는 것도 귀찮아."

[피하고 싶은 것]
플레이어: "싫어하는 건 있어요?"
NPC: "기름진 건 오늘 좀 힘들어."
```

질문 대화는 너무 길어지면 안 된다. 목표는 잡담이 아니라, 손님과 실제로 대화하고 있다는 감각을 주면서 추론 단서를 자연스럽게 전달하는 것이다.

권장 길이:

```text
일반 질문: 2줄
관계/재방문 질문: 3~4줄
스토리/호감도 이벤트 질문: 필요 시 4줄 이상 가능
```

## 8. 호감도 시스템

호감도는 내부적으로 점수로 관리하고, 기획/표시는 단계로 관리한다.

```text
내부 처리: Affinity Score 0~100
기획/표시: Affinity Level 0~5
```

기본 단계안:

| 단계 | 점수 | 의미 |
| --- | ---: | --- |
| Level 0 | 0~9 | 낯선 손님 |
| Level 1 | 10~24 | 안면 있음 |
| Level 2 | 25~44 | 이름을 기억함 |
| Level 3 | 45~64 | 믿고 맡김 |
| Level 4 | 65~84 | 단골 |
| Level 5 | 85~100 | 특별 의뢰 가능 |

요리 결과에 따른 변화:

| 결과 | 호감도 변화 |
| --- | ---: |
| 괴식 | 0 |
| 비정답 | 0 |
| 유사 정답 | +5 |
| 정답 | +15 |
| 완벽한 정답 | +25 |

프로토타입에서는 Cozy 감각을 유지하기 위해 괴식이어도 호감도를 깎지 않는다. 대신 반응, 기록, 재방문 대사에서 실패를 표현한다.

호감도 보상:

```text
Level 0
- 질문 1회
- 질문 가능 카테고리: 맛 / 온도·식감 / 몸 상태

Level 1
- 질문 2회
- 피하고 싶은 것 카테고리 해금
```

정식 확장 예시:

```text
Level 2: 이전 방문 기억 대사
Level 3: 출신/문화 질문 해금
Level 4: 단골 대사, 약한 기억 이벤트 증가
Level 5: 특별 의뢰 해금
```

## 9. 정답 판정

정답 판정은 혼합 방식으로 처리한다.

```text
정답: 직접 지정 레시피
유사 정답: 음식 종류 + 필수 태그 + 보너스 태그
비정답: 핵심 조건 불충족
괴식: 금지 조합/금지 손질법
```

판정 순서:

```text
1. 괴식 조건 검사
2. 정답 레시피 검사
3. 유사 정답 조건 검사
4. 그 외는 비정답
```

예시:

```text
정답 레시피: 허브 슬라임 스무디
허용 음식 종류: 음료, 디저트
필수 태그: 달콤함
보너스 태그: 차가움, 부드러움, 가벼움
금지 태그: 기름짐, 쓴맛
괴식 조건: 슬라임 젤리 굽기
```

## 10. 재방문 기억 이벤트

프로토타입에서는 유사 정답 이상이면 재방문 기억 이벤트가 발생할 수 있게 한다.

```text
조건: LastServedResult >= Similar
```

저장할 결과 등급:

```text
Wrong
Similar
Correct
Perfect
```

지금은 단순히 `유사 정답 이상`으로 처리하지만, 나중에 다음처럼 확장할 수 있다.

```text
Similar → 약한 기억 이벤트
Correct / Perfect → 강한 기억 이벤트
```

## 11. 연속 이벤트

특정 NPC는 여러 차례에 걸쳐 이어지는 Visit Event Chain을 가질 수 있다.

```text
Chain ID: Yorn_TribeFeast
Step 1: 부족 잔치를 언급
Step 2: 필요한 요리 단서를 제공
Step 3: 특별 의뢰 제안
```

규칙:

- 중요한 체인은 강제 또는 최우선 진행한다.
- 가벼운 체인은 우선 후보로만 섞는다.
- 체인 단계는 각각 별도 Visit Event로 작성한다.
- 체인 이벤트는 대체로 `NeverRepeat`로 둔다.

## 12. 의뢰 시스템 연결

의뢰는 지금 단계에서 상세 설계하지 않는다.

현재는 호감도 Level 5에서 열리는 장기 보상 자리만 둔다.

```text
Level 5 도달
→ 특별 의뢰 해금 Visit Event 발생
→ 이후 해당 NPC는 의뢰 가능 NPC가 됨
```

NPC Sheet에는 다음 항목만 둔다.

```text
Request Available
Request Unlock Level
Request Unlock Event
```

## 13. 프로토타입 범위

프로토타입 기준:

```text
지역: 이끼 동굴 1개
하루 손님 수: 3명
NPC: 3명
Visit Event: 기본 3개 + 재방문/호감도 샘플 2개 = 총 5개
질문 카테고리: 맛 / 온도·식감 / 몸 상태 / 피하고 싶은 것
호감도: Level 1 효과까지 구현
판정: 정답 / 유사 정답 / 비정답 / 괴식
```

프로토타입 NPC:

```text
지친 초보 모험가
- 첫 방문 이벤트
- 호감도 Level 1 인사 이벤트
- 재방문 기억 이벤트

광산길 정찰병
- 첫 방문 이벤트

겁 많은 마법 견습생
- 첫 방문 이벤트
```

## 14. 스프레드시트 시트 구성

하나의 스프레드시트 파일 안에 다음 시트를 둔다.

```text
NPC
VisitEvents
DialogueLines
RegionPools
Recipes
QuestionCategories
Enums
```

각 행은 하나의 데이터 단위다.

```text
NPC Sheet: 한 줄 = NPC 한 명
VisitEvents Sheet: 한 줄 = Visit Event 하나
DialogueLines Sheet: 한 줄 = 대화 한 줄
RegionPools Sheet: 한 줄 = 지역 Pool 항목 하나
Recipes Sheet: 한 줄 = 레시피 하나
QuestionCategories Sheet: 한 줄 = 질문 카테고리 하나
```

`VisitEvents`는 이벤트의 조건, 판정, 보상 같은 뼈대를 관리한다. 실제 대화는 `DialogueLines`에서 줄 단위로 관리한다.

```text
DialogueLines
- Event ID
- Dialogue Group
- Line Order
- Speaker
- Text
- Purpose
- Question Category
```

Dialogue Group 예시:

```text
Intro: 기본 인사/관계 대화
OrderIntent: 주문 의도가 드러나는 대화
Question_Taste: 맛 질문을 선택했을 때 출력되는 질문 대화
Question_TextureTemp: 온도/식감 질문 대화
Question_Condition: 몸 상태 질문 대화
Question_Avoid: 피하고 싶은 것 질문 대화
Result_Correct: 정답 반응
Result_Similar: 유사 정답 반응
Result_Wrong: 비정답 반응
Result_Disgusting: 괴식 반응
```

이렇게 분리하면 대화가 길어져도 Visit Event 표가 지나치게 복잡해지지 않는다. 또한 같은 이벤트 안에서 기본 대화와 질문 대화를 명확히 나눌 수 있다.

## 15. 피드백할 지점

피드백 시 아래 항목을 우선 확인하면 좋다.

- Visit Event 중심 구조가 직관적인가?
- NPC 방문이 주문 접수가 아니라 대화 장면처럼 느껴지는가?
- 질문 카테고리가 너무 적거나 많지 않은가?
- 질문 카테고리를 눌렀을 때 나오는 질문 대화가 충분히 자연스러운가?
- 유사 정답 판정이 납득 가능한가?
- 호감도 Level 1 보상이 체감될 것 같은가?
- 재방문 이벤트 조건을 `유사 정답 이상`으로 둔 것이 적절한가?
- 하루 손님 3명 고정 구조가 게임 분위기에 맞는가?
- 프로토타입 범위가 4주 내 검증에 적당한가?
